# Проектная документация

## Функциональные требования

**FR-1. Каталог комплектующих.** Система должна предоставлять каталог комплектующих с разделением по категориям (`component_categories`) и фильтрацией по техническим характеристикам.

**FR-2. Создание конфигурации.** Пользователь должен иметь возможность выбирать, заменять и удалять комплектующие в соответствующих слотах сборки.

**FR-3. Проверка совместимости.** Система должна автоматически проверять совместимость выбранных компонентов: сокеты процессора и материнской платы, тип оперативной памяти, длину видеокарты и высоту кулера относительно ограничений корпуса, а также достаточность мощности блока питания.

**FR-4. Расчёт мощности.** Система должна рассчитывать оценку энергопотребления на основе характеристик выбранных компонентов и показывать запас мощности блока питания. Результат должен обновляться при изменении состава сборки.

**FR-5. Видимость сборки.** Автор должен иметь возможность переключать сборку между приватным и публичным режимами. Приватная сборка доступна только автору, публичная отображается в общем каталоге.

**FR-6. Ссылка на сборку.** Для каждой сборки система должна формировать постоянный уникальный идентификатор `share_slug`. Публичную сборку можно просматривать по ссылке без авторизации. Ссылка на приватную сборку не предоставляет доступ посторонним пользователям.

## Нефункциональные требования

**NFR-1. Развёртывание и ресурсы.** Приложение, включая обратный прокси, клиентскую часть, серверное API и PostgreSQL, должно развёртываться через Docker Compose на Arch Linux с 8 ГБ оперативной памяти. Суммарное потребление оперативной памяти работающими контейнерами не должно превышать 1,5 ГБ.

**NFR-2. Производительность.** Время серверной проверки совместимости полной конфигурации не должно превышать 150 мс. Передача данных по сети в это время не входит.

**NFR-3. Целостность данных.** При удалении комплектующего из каталога соответствующие ссылки в сборках должны сбрасываться в `NULL` с помощью `ON DELETE SET NULL`. Сама сборка должна сохраняться, а её признак `is_compatible` — изменяться на `false`. Обновление состояния сборки выполняется сервером в рамках той же транзакции.

**NFR-4. Интерфейс.** Интерфейс должен поддерживать ширину окна от 1280 пикселей. Основные области конструктора, характеристики компонентов и результаты проверки должны оставаться читаемыми и доступными для взаимодействия.

**NFR-5. Логирование.** Сервер должен записывать входящие запросы, ошибки, события авторизации и изменения данных. Запись журнала должна содержать время, уровень события, его описание и идентификатор запроса. Пароли, access-токены и refresh-токены не должны попадать в журналы. Для ограничения занимаемого места должна быть настроена ротация логов.

**NFR-6. Технологический стек.** Текущий прототип использует HTML, CSS и JavaScript. Тестовый каталог хранится в отдельном файле data/components.js, проверка совместимости выполняется в браузере. Серверная часть на Python и PostgreSQL относятся к следующим этапам.

**NFR-7. Числовые типы данных.** Для небольших целочисленных значений в БД следует использовать `SMALLINT` вместо `INTEGER`: мощности и TDP, размеров компонентов в миллиметрах, объёма памяти, количества модулей и слотов RAM, порядка отображения категорий. Для каждого поля задаются допустимые границы через `CHECK`. Диапазон `SMALLINT` — от −32768 до 32767; вычисления выполняются в более широком типе с проверкой результата перед сохранением. Идентификаторы сущностей сохраняют тип UUID.

**NFR-8. Хранение refresh токенов.** Для обновления пользовательского сеанса в БД должна быть предусмотрена отдельная таблица `refresh_tokens` с полями `id`, `user_id`, `token_hash`, `created_at`, `expires_at` и `revoked_at`. Таблица связывается с пользователем по `user_id`. В БД хранится только хеш токена. Истёкший или отозванный токен не должен позволять обновить сеанс; при выходе пользователя соответствующий токен отзывается.

## Бизнес требования

**BR-1. Назначение продукта.** Предоставить веб-сервис для подбора комплектующих ПК с автоматической проверкой их физической, интерфейсной и электрической совместимости. Оформление заказов, корзина и оплата в сервисе не предусмотрены.

**BR-2. Польза для пользователя.** Помочь пользователю избежать ошибок при подборе комплектующих: несовпадения сокетов, неподходящего типа памяти, превышения допустимых размеров и недостаточной мощности блока питания.

**BR-3. Сохранение и обмен сборками.** Предоставить возможность сохранять конфигурации, управлять их видимостью и делиться публичными сборками по постоянной ссылке.

**BR-4. Единый каталог.** Обеспечить единый каталог категорий и комплектующих с характеристиками, необходимыми для выбора и проверки совместимости.

**BR-5. Реклама.** Предусмотреть монетизацию сервиса за счёт размещения рекламы производителей комплектующих и магазинов. Рекламные материалы должны быть явно обозначены и не должны влиять на результаты проверки совместимости или мешать основным действиям пользователя.

## План разработки

### Этап 1 Лабораторная работа 1

- Анализ предметной области и определение назначения приложения.
- Описание основных сценариев использования.
- Подготовка концептуальной схемы данных.

### Этап 2 Лабораторная работа 2

- Подготовка требований и ERD.
- Создание макета интерфейса конфигуратора.
- Подготовка каркаса клиентской и серверной частей.

### Этап 3 Лабораторная работа 3

Цель — подготовить локальный прототип сайта, работающий в браузере без серверной части и БД.

- Подготовка тестового каталога комплектующих в отдельном JavaScript-файле.
- Подключение локального каталога к интерфейсу.
- Реализация выбора, замены и удаления компонентов из сборки.
- Реализация проверок в браузере: совпадение сокетов, соответствие типа RAM и достаточность мощности БП.
- Отображение результатов проверки и сообщений об ошибках.

Результат этапа: пользователь может открыть сайт локально, выбрать комплектующие из тестового каталога и получить результат базовой проверки совместимости.

### Этап 4 Доработка после ЛР3

- Создание серверной части на Python и перенос проверки совместимости на сервер.
- Определение основных маршрутов API.
- Подключение PostgreSQL, создание миграций и перенос тестового каталога в БД.
- Реализация регистрации, входа и обновления сеанса через refresh-токены.
- Добавление сохранения и редактирования сборок в БД.
- Реализация приватного и публичного доступа, постоянных ссылок и комментариев.
- Добавление геометрических проверок совместимости.
- Настройка логирования и добавление рекламных размещений.

### Этап 5 Подготовка к защите

- Проверка основных сценариев и исправление ошибок.
- Подготовка Docker Compose и инструкции запуска.
- Развёртывание приложения и проверка потребления ресурсов.
- Обновление документации и подготовка демонстрации.
